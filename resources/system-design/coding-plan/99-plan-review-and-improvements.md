## Executive Summary

This review uncovered **65+ distinct issues** across the IoT Vehicle Tracking System coding plans, categorized as **9 CRITICAL**, **18 HIGH**, **16 MEDIUM**, and **6 LOW** severity findings. Three systemic failures stand out:

1. **CLAUDE.md is fundamentally out of sync with all plan documents** — it describes a different project structure (`/iot-vehicle-tracking-system/backend/` vs `Tracking_Backend/`), different commands (`npm run install:all` vs per-service installs), and different Docker strategies. Every AI agent using CLAUDE.md as entry point will start in the wrong directory.

2. **The MQTT Bridge has no single source of truth** — three documents place it in three different locations (inside `backend/src/`, at repo root `mqtt-bridge/`, or as `Tracking_MqttBridge/`). Its import paths reference backend internals (`@/infrastructure/logger`) that are impossible if it's truly standalone.

3. **Critical security vulnerabilities exist in the plan** — session tokens stored in plaintext, no MQTT ACL rules (any authenticated client sees all device data), default passwords that silently work in production, unauthenticated `/metrics` and `/iot` WebSocket endpoints, and SQL injection via unsanitized column names.

Additionally, **~50% of the backend business logic** (vehicle, customer, trip, alert, geofence, maintenance domains) has no implementation phase assigned, and the frontend architecture has a REST-overwrites-WebSocket race condition that will cause visible UI glitches under normal usage.

### 2.1 Backend vs Frontend: API Contract Mismatches

| Conflict | Backend Says | Frontend Expects | Resolution |
|----------|-------------|-----------------|------------|
| **URL naming** | `/device/list`, `/device/manage` (IVM26 legacy, singular) | Standard REST (`/devices`, `/devices/:id`) | **Adopt REST conventions.** The IVM26 pattern creates unnecessary confusion. |
| **Auth token format** | Session token in `Authorization: Bearer <token>` header | Zustand stores token in `auth-storage` localStorage key; Mobile writes to `auth_token` key | **Unify:** Backend issues session token -> Frontend stores in Zustand persist (`auth-storage`) -> Mobile bridge writes to same key via JS bridge, not `evaluateJavascript` |
| **WebSocket events** | Backend emits `status:update`, `alert:new`, `session:update`, `data:realtime` on namespaces `/devices`, `/dashboard`, `/iot` | Frontend hooks listen for `device.status.changed`, `alert.created`, `telemetry:{deviceId}` | **MISMATCH.** Create `24-websocket-events.md` with authoritative event contract. Both sides must use identical names. |
| **Telemetry field names** | VictoriaMetrics: `device_latitude`, `device_speed`; API response: `lat`, `spd` | Frontend expects... unclear (no response mapping documented) | **Create data dictionary** mapping field names across all layers. |
| **Position data refresh** | Backend provides `GET /devices/positions` (all at once, no pagination) | Frontend polls every 10s AND receives WebSocket updates for same data | **Race condition.** Disable polling when WebSocket connected. Add viewport-based loading to API. |

### 2.2 Security vs Backend: Security Requirements vs Performance

| Conflict | Security Demands | Backend Impact | Resolution |
|----------|-----------------|---------------|------------|
| **Device auth per message** | Validate auth token on every MQTT message | 500 DB queries/sec at scale for auth alone | **Cache auth results** in DeviceStateCache with 5-min TTL. Security maintains integrity; performance is acceptable. |
| **Session token hashing** | Store SHA-256 hash, not plaintext | Every `authenticateRequest` must hash the incoming token before DB lookup | **Acceptable overhead.** SHA-256 is <1us. Security wins. |
| **10KB body limit** | Prevent DoS via large payloads | Firmware upload needs >10KB | **Route-specific limits.** 100KB default, 50MB only on `POST /firmware/:id/upload`. |
| **TLS for internal MQTT** | All MQTT connections must use TLS | Adds latency and CPU overhead to every message | **Use TLS in production**, plaintext only in `NODE_ENV=development` with explicit guard. |
| **Container resource limits** | Memory/CPU limits on every container | May cause OOM kills during traffic spikes | **Set generous limits** (2x expected usage). Better to OOM-kill one container than take down the host. |
